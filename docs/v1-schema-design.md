# AgenticShop V1 schema design

## Scope

This is the business data the first SQL-enabled analyst can investigate. It intentionally excludes LLM state, tool traces, RAG documents, and evaluation records.

All monetary amounts are INR and use `numeric(12,2)`. Dates use `date`, because V1 questions analyse business days and months rather than time-of-day behaviour.

## Relationships

```text
customers 1 ──< orders 1 ──< order_items >── 1 products
                       └──< refunds
```

## Tables

### customers

| Column | Type | Notes |
|---|---|---|
| `customer_id` | `bigint` | Primary key, generated by the database |
| `name` | `text` | Synthetic customer name |
| `signup_date` | `date` | Date the customer registered |
| `region` | `varchar(50)` | `North`, `South`, `East`, or `West` in V1 seed data |
| `city` | `varchar(50)` | Needed to answer questions such as “How many orders came from Delhi?” |

`city` is an intentional addition to the original draft: a region alone cannot answer city-level questions while also supporting North-region analysis.

### products

| Column | Type | Notes |
|---|---|---|
| `product_id` | `bigint` | Primary key, generated by the database |
| `product_name` | `text` | Product display name |
| `category` | `varchar(100)` | For example: Electronics, Fashion, Home, Beauty |
| `price` | `numeric(12,2)` | Current catalogue price; not used for historical revenue |

### orders

| Column | Type | Notes |
|---|---|---|
| `order_id` | `bigint` | Primary key, generated by the database |
| `customer_id` | `bigint` | Foreign key to `customers` |
| `order_date` | `date` | Date the order was placed |
| `status` | `varchar(20)` | One of `completed`, `pending`, or `cancelled` |
| `total_amount` | `numeric(12,2)` | Sum of item line amounts, before refunds |

### order_items

| Column | Type | Notes |
|---|---|---|
| `order_item_id` | `bigint` | Primary key, generated by the database |
| `order_id` | `bigint` | Foreign key to `orders` |
| `product_id` | `bigint` | Foreign key to `products` |
| `quantity` | `integer` | Must be greater than zero |
| `unit_price` | `numeric(12,2)` | Price actually paid per item at purchase time |

`unit_price`, not `products.price`, is the source of truth for historical product and category revenue. This keeps past revenue correct if catalogue prices change later.

### refunds

| Column | Type | Notes |
|---|---|---|
| `refund_id` | `bigint` | Primary key, generated by the database |
| `order_id` | `bigint` | Foreign key to `orders` |
| `refund_date` | `date` | Date the refund was issued |
| `amount` | `numeric(12,2)` | Positive partial or full refund amount |
| `reason` | `varchar(100)` | Synthetic refund reason |

Multiple partial refunds may belong to one order. Seed validation will ensure their total never exceeds the order total.

## V1 business definitions

| Term | Definition |
|---|---|
| Revenue | `SUM(orders.total_amount)` for `completed` orders; refunds are not subtracted |
| Net revenue | Revenue minus refunds; deferred until a later question explicitly asks for it |
| Orders received | Count of all orders placed, regardless of final status |
| Completed orders | Count of orders with `status = 'completed'` |
| Product/category revenue | Sum of `quantity × unit_price` for items in completed orders |
| Customer sign-ups | Count of customers by `signup_date` |

## Deliberate V1 omissions

- No separate `categories`, `regions`, or `cities` tables.
- No inventory, promotions, shipment, tax, discount, marketing, or checkout-event data.
- No agent state, messages, traces, approval, or evaluation tables.
- No RAG documents or vector embeddings.

These are introduced only when a later capability needs them.

## Seed-data rules for the next step

1. Use a fixed random seed, so a reset generates the same dataset.
2. Generate dimensions first: products and customers.
3. Generate orders, items, and refunds with valid foreign keys.
4. Make `orders.total_amount` exactly equal to the sum of its item lines.
5. Encode a known business story: stable July, strong August, then a September decline driven by Electronics, North-region demand, and increased refunds.
6. Verify the seeded facts with SQL assertions before using them in LLM evaluations.
